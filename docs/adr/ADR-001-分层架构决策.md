# ADR-001：分层架构决策

> 状态：已采纳  
> 日期：2026-08-12  
> 决策者：团队架构组

---

## 一、背景

Team Portal Lite 是一个内部教学练习项目，目标是搭建一个团队内部门户，包含公告卡片、待办清单、寿星展示等功能模块。项目虽然规模不大（10 人小团队），但需要为后续两天的练习（Day22 写组件、Day23 做性能优化）准备干净、规整的代码容器。

当前面临的核心问题：

1. **代码归属不清**：如果所有代码塞进一个目录，新人无法区分"通用零件"和"具体业务"，后续维护时容易把业务逻辑写进通用组件，导致耦合蔓延。
2. **依赖关系混乱**：如果不强制约束依赖方向，通用 UI 组件可能反向引用业务模块，形成循环依赖，导致编译死循环和维护噩梦。
3. **技术选型需要白纸黑字**：团队成员可能对"为什么用 pnpm 而不是 npm""为什么用 App Router 而不是 pages/"有疑问，需要一份决策记录避免后期反复争论。

因此，我们需要在写第一行业务代码之前，确定项目的分层架构方案，并记录决策理由。

---

## 二、备选方案

### 方案 A：单仓单应用（Single Repo, Single App）

将所有代码放在一个 Next.js 项目中，不做物理分层，所有组件、工具函数、业务逻辑都放在 `src/` 目录下，通过文件夹命名约定区分。

```
team-portal-lite/
└── src/
    ├── components/    # 所有组件混在一起
    ├── utils/         # 工具函数
    ├── app/           # 页面
    └── lib/           # 其他逻辑
```

**优点：**
- 初始搭建简单，不需要配置 workspace 和多包管理。
- 一个 `package.json` 管理所有依赖，新手入门门槛低。

**缺点：**
- 没有物理隔离，仅靠口头约定和文件夹命名，无法防止通用组件引用业务代码。
- 随着功能增加，`components/` 目录会变成"大杂烩"，无法区分哪些是通用零件、哪些是业务组件。
- 无法独立编译和测试各个模块，构建缓存粒度粗，Turbo 等工具无法发挥优势。
- 循环依赖风险高，ESLint 规则难以精确到包级别。

---

### 方案 B：Monorepo 4 层分层架构

使用 pnpm workspace 将项目拆分为 1 个主站 + 3 个共享包，每层有独立的 `package.json`，在物理层面隔离，并通过 ESLint 规则强制约束依赖方向。

```
team-portal-lite/
├── apps/
│   └── web/               # Next.js 14 主站（页面组装层）
├── packages/
│   ├── ui/                # 通用 UI 零件（无业务逻辑）
│   ├── lib/               # 工具函数（无 UI 依赖）
│   └── features/          # 业务零件层（预留）
├── pnpm-workspace.yaml
└── turbo.json
```

**优点：**
- 物理隔离：每个"隔间"有独立的 `package.json`，什么代码该放哪里一目了然。
- 依赖方向可控：通过 ESLint `import/no-restricted-paths` 规则自动拦截跨层引用。
- 构建缓存：Turbo 可以按包粒度缓存，没改过的包直接复用缓存，构建速度快。
- 可扩展性强：后续添加新业务模块只需在 `packages/features/` 中新增，不影响现有结构。
- 新人友好：目录结构即文档，10 分钟内就能理解代码该放哪。

**缺点：**
- 初始配置较多：需要配置 workspace、Turbo、ESLint 规则、多个 `tsconfig.json`。
- 需要理解 monorepo 概念：对从未接触过 workspace 的新人有一定学习成本。

---

## 三、最终选择

**选择方案 B：Monorepo 4 层分层架构。**

4 层架构的职责定义如下：

| 层级 | 目录 | 职责 | 依赖规则 |
|------|------|------|----------|
| **主站层** | `apps/web` | Next.js 14 主站，页面组装层，只做组件拼装和数据传递 | 可以引用 `features`、`ui`、`lib` |
| **业务零件层** | `packages/features` | 包含具体业务逻辑的模块（公告、待办、寿星等） | 可以引用 `ui`、`lib`，不能引用 `apps` |
| **通用零件层** | `packages/ui` | 通用 UI 零件（按钮、卡片、头像等无业务逻辑的组件） | 可以引用 `lib`，不能引用 `apps`、`features` |
| **工具层** | `packages/lib` | 工具函数、通用逻辑（纯 TypeScript，无 UI 依赖） | 不能引用任何上层包 |

依赖方向严格遵循单向楼梯：

```
apps/web → packages/features → packages/ui → packages/lib
```

技术选型：
- **包管理**：pnpm + workspace 协议（`workspace:*`）
- **主框架**：Next.js 14 App Router（`app/` 目录）
- **构建加速**：Turbo（任务缓存）
- **代码检查**：ESLint + `import/no-restricted-paths`
- **编程语言**：TypeScript 严格模式
- **代码风格**：Prettier

## 四、选择理由

### 为什么选 Monorepo 4 层而不是单仓单应用？

本项目的核心目标不是快速写出功能，而是**练习前端架构设计全流程**。单仓单应用虽然起步简单，但无法达到"让新人清晰理解什么代码该放什么位置"的目标。物理隔离 + ESLint 规则的双重保障，能让架构约束从"口头约定"变成"自动拦截"，这正是本项目最核心的练习价值。

### 为什么用 pnpm 而不是 npm/yarn？

1. **省空间**：pnpm 使用硬链接和符号链接存储依赖，不同项目共享同一份依赖文件，磁盘占用远小于 npm/yarn。
2. **速度快**：pnpm 的安装速度在大多数场景下优于 npm 和 yarn（尤其 Yarn Classic）。
3. **workspace 协议**：pnpm 原生支持 `workspace:*` 协议，内部包引用时能自动链接到本地源码，不需要发版或手动配置路径，这是 monorepo 的关键能力。
4. **严格的依赖管理**：pnpm 默认使用符号链接，只有在 `package.json` 中显式声明的依赖才能被引用，避免"幽灵依赖"问题。

### 为什么用 Next.js 14 App Router 而不是 pages/？

1. **App Router 是 Next.js 的未来方向**：Next.js 14 中 App Router 已稳定，官方推荐新项目使用。
2. **与实战项目对齐**：后续第 25 天的实战项目使用同款框架，提前练习 App Router 有直接价值。
3. **更好的组件化支持**：App Router 的布局系统、服务端组件、流式渲染等特性能更好地支持分层架构。
4. **`pages/` 是旧模式**：虽然仍兼容，但新项目不应再使用旧模式。

### 为什么用 Turbo？

Turbo 能按包粒度缓存构建结果。在 monorepo 中，如果只改了 `packages/lib` 的代码，Turbo 只会重新构建 `lib` 及其依赖链上的包，`packages/ui` 等未改动的包直接复用缓存，大幅提升构建和 lint 的速度。

### 为什么依赖方向必须是单向的？

如果允许底层包引用上层包（例如 `packages/ui` 引用 `apps/web`），就会形成循环依赖。循环依赖会导致编译时死循环、运行时模块为 `undefined`、代码难以理解和测试。严格执行"上层引用下层"的单向规则，能从根本上杜绝这个问题。如果发现两个模块必须互相调用，说明这部分公共代码应该抽到更下层的 `packages/lib` 中。
